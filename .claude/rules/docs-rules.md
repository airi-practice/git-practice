# 説明書記載ルール

## 1. このPJの目的

このPJは、プログラミングを学び始めたばかりの初学者が、Gitの基本の概念と実務でよく使用する操作方法を理解すること。
コマンドを覚える事が目的ではなく、各操作の原理と意味を理解する事が目的である。
単なる説明書ではなく、プログラミングの授業のように、基礎から順番にハンズオン形式で学べる内容とする。
mdファイルを記載する場合は、必ず [natural-japanese](../skills/natural-japanese/SKILL.md) スキルをロードして使用すること。

## 2. 読者の前提知識

読者はプログラミングの知識やIT知識が全くない初学者であることを前提とする。
PCの基本操作（マウス、キーボード、ファイル操作）ができることを前提とする。
以下の知識は持っていないものとして説明する。

- Gitの概念や操作方法
- GitHubの概念や操作方法
- プログラミングの概念や操作方法
- システム開発が何か
- アプリケーションやインフラという概念、ITの基礎知識
- ファイル形式や競合という概念
- ネットワーク通信

### 3. 初学者目線で説明する

- 専門用語をいきなり使用しない。
- 専門用語を使用する場合は、最初に日常的な言葉で意味を説明する。
- 初学者が理解できないことを前提に、説明を省略しない。
- 「なぜ必要なのか」「何のために存在するのか」を必ず説明する。
- Gitの知識と結びつけながら説明する。
- 一度説明した概念も、実際のファイルが登場したときには必要に応じて再説明する。
- 専門用語そのものを禁止するわけではない。ReactやSpringなど、実際の技術名称は正しく使用し、その役割を分かりやすく説明すること。
- 実際に存在するファイル名をリポジトリルートからの相対パスで記載する。
- 一般的なGitの仕組みと、このシステム固有の実装を区別する。
- `.claude/` については、学習者に関係しないため、全章で一切触れない。
- **【重要】** 混乱を避けるため、本質部分の理解をする上で今は理解していなくても理解を進める事ができる内容を説明しないこと。知識を詳細に全て説明する事はしなくてよい。細かい知識よりも大枠の知識を早く理解できるようにサポートする事を意識する。（例: WEBアプリの知識を教える際に本質的な「サーバー」や「クライアント」の概念の説明は重要だが、HTTPS通信の仕組みやプロトコルの種類などはWEBアプリの仕組みを理解する上で最初は一旦理解しなくても進むことができるため、割愛するべき。）
- **【重要】** 抽象的な概念は、身近なものに例えて分かりやすく説明すること。例え話をした後は、必ずたとえ話が元の概念の何に対応する例えなのかを明示すること。例え話をする際は必ず絵を使用すること。

### 4. 図や絵を積極的に使用する

文章だけで説明しないこと。
図（SVG）を積極的に使用し、以下の図を絵として作成すること。
なお、シーケンスを説明する際は、Mermaid のシーケンス図を使用すること。
説明文が3行以上続く場合は、必ず図や絵を挿入して説明すること。
SVG画像を作成する際は スキル「svg-art」をロードした上で、[svg-rules.md](./svg-rules.md) に従うこと。

- システム全体の構成図や概念図
- 処理や作業の流れ、手順
- ファイル構成・役割の対応図
- 画面の操作（画面遷移やボタンの押下など）のイメージ
- 図の中にも専門用語だけを並べず、何をしているのかが分かる日本語を添えること。

図の形式は、次のように使い分ける。

- 流れ・順番・関係・ファイルの対応を見せる図（flowchart）は、SVG で書く。見た目をそろえ、分かりやすくするため。
- やり取りの順番を見せるシーケンス図（sequenceDiagram）は、Mermaid で書く。Markdown 上で表示でき、あとから直しやすいため。
- 文字列を部分に分けて見せる図、並べて対応づける図、入れ子や配置を見せる図のように、見た目が分かりやすさに関わるものも、SVG で書く。
- SVG は `docs/images/` に置き、`![代替テキスト](../images/xxx.svg)` で読み込む。Mermaid から置き換えた図の名前は、`<章の2桁>-flow-<連番2桁>-<短い英語名>` にする。作り方は `.claude/rules/svg-rules.md` と `tools/svg/` に従い、図の内容（文言・矢印の向き・グループ）は、Mermaid のときから変えない。
- Mermaid から置き換えた図には、猫の吹き出しを付けない（内容を変えないため）。
- SVG の代替テキストには、図が伝える内容を文で書く。
- SVG の `<text>` は、行頭の空白を詰めてしまう。ファイルの字下げを見せる図では、行頭の空白を `&#160;` に書き換える。
- 図の中の文字も、専門用語だけを並べず、何をしているのかが分かる日本語を添える。

## 5. 文体・表現

- まず結論を述べる。
- です・ます調は禁止。
- 「～だよ」「～なんだ」「～してみよう」「～ということだね」など、講師が初学者に教えるような自然な口調にする。
- 子供向けのような過度に幼い表現にはしない。
- 説明は簡潔にしつつ、必要な情報は省略しない。
- 一つの段落で複数の概念を説明しない。
- 難しい概念は、身近な具体例やたとえ話を使って説明する。
- 英語の専門用語には、必要に応じて日本語の意味を添える。
- 長文は禁止。説明が長くなる場合は、箇条書きまたは短文を複数に分けて記載する。

## 6. 説明内容のチェック

- 初学者が最初から順番に読むだけで理解できる構成にする。
- 実際のファイル内容と説明内容に矛盾がないこと。
- 図と文章の内容が一致していること。
- 専門用語を説明なしで登場させないこと。
- 一般論とこのシステム固有の仕様を混同しないこと。
- 説明を省略して「詳しくはファイルを見て」と済ませないこと。
- 最後に、資料全体を読み直し、Git初学者の視点で理解できない箇所、説明が飛躍している箇所、ファイルと説明が一致していない箇所がないか自己レビューして修正すること。

## 7. 実践手順書を作る場合の要件

Gitの操作の手順について聞かれた際は、特に以下を厳守すること。

- 質問者自身が問いを明確にできていない可能性がある。聞きたい内容を明確にしてから説明する。
- 実際に存在するディレクトリ・ファイル構成に合わせる。
- 存在しないファイル名を勝手に作らない。
- 実際のプロジェクトで使用している手順に合わせる。
- 各ファイルの記述場所を明示する。
- 既存ファイルの変更箇所を明示する。
- なぜその操作をすべきなのかを説明する。

## 8. 復習セクションを必ず記載

- 一つ説明するごとにひとつ復習セクションを必ず挟むこと。(例: 単位は①〜〜の説明と②〜〜の間や、###〜〜と###〜〜の間など)
- その章で教えたことの内容の短文の要約を箇条書きで穴あきの問題で出すこと。（例: WEBアプリケーションは、(    )で操作して利用するソフトである。→答えは「ブラウザ」）
- 復習の答えはアコーディオンで閉じて置き、読者が自分で考える余地を残すこと。
- 復習のエリアはTIPエリアで表現すること。

復習セクションを記載したら必ず下記観点でセルフチェックする。

- 答えが、その節の本文と合っているか。
- 復習を置いた位置が自然か。節の末尾に置いているので、見出しの名前と復習の内容が少しずれて見える箇所がないか。
- 本文が短い節の復習が、本文をなぞるだけになっていないか。

以下、記載例
```
> [!TIP]
> **復習**
>
> - WEBアプリケーションは、（　　　）で操作して使うソフトである
> - お願いを出す側を（　　　）と呼ぶ
> - お願いを受けて情報を返す側を（　　　）と呼ぶ
>
> <details>
> <summary>答えを見る</summary>
>
> 1. ブラウザ
> 2. クライアント
> 3. サーバー
>
> </details>
```
